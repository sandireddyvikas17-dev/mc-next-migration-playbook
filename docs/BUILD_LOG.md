Personal portfolio design study for the fictional *Northstar Credit Union*. Honest framing throughout: no Marketing Cloud Next production experience is claimed; this is a migration design study built from real Marketing Cloud Engagement + Data Cloud experience. Not employer work.

## Day 2 — Data & consent on Data 360 (Nov 17, 2026)

- Built `data-360/` with four files: `README.md` (Day 2 overview), `segment-definitions.md`, `consent-preference-sync-design.md`, and `data-action-triggers.md`.
- Segments: rebuilt every Moves-feeding Engagement audience as a Data Cloud segment on the unified profile — SEG-01 New Members (from DE-01/Q-01, staff exclusion carried), SEG-02 Card Issued Not Activated (batch companion to the event entry), SEG-03a/03b CD Maturity Window + Savings Goal Stalled (from DE-02/Q-04), SEG-04 Dormant 90+ using SQL Q-03's dormancy definition verbatim (no login and no transaction in 90+ days), and SEG-00 Global Suppression as the named exclusion set. Added the parity rule Day 3 will use: differences are investigated as definition → data completeness → identity → consent, in that order.
- Consent sync: Data 360 named the consent system of record on the unified profile; CP-01 stays as the capture surface writing into it. Bidirectional sync for consent and subscriptions (most recent explicit member action wins, opt-outs never overwritten by late opt-ins), one-directional most-restrictive-wins for suppression. DE-05 rebuilt as suppression state on the unified profile, enforced at three gates (segment build, activation/Data Action, send), with a reconcile-with-DE-05 criterion before any Moves cutover.
- Data Actions: specs DA-01–DA-06 — card-issued event (INT-02 payload reused), new-member and maturity/goal segment entries, dormant entry with a pre-send activity re-check, a shared exit-event pattern, and a suppression-change hold. Universal guardrails: consent re-check at trigger time, dedupe keys per spec, one entry path per Flow, marketing triggers pause if consent sync is degraded. No specs for J-03, J-07, J-06, or A-04 — Stays and Retires get no triggers.
- Carried forward the five items deferred from Day 1's gap check, each by name: (1) communication subscriptions — every Engagement list/publication list mapped per channel, email and SMS in separate decisions, All Subscribers mapped to channel consent (not a subscription) and the service list deliberately unmapped; (2) per-DE sync verdicts — no audience DE syncs as-is; each is rebuilt from source, ingested as dates/attributes, synced for reference (DE-03), or rebuilt as profile state (DE-05); (3) shared sending domains — both platforms send from the same authenticated domains during coexistence, classifications kept distinct, no authentication changes inside a cutover wave; (4) legacy-compatibility flags per DE and per segment (INT-02 payloads and DE-04 activity usable as-is with conditions; DE-01/02/03/05 require transformation); (5) test-environment note — Engagement tests in live-org structures, Next/Data 360 tests against data spaces/test profiles, so consent-sync testing uses invented test members changed deliberately in each surface and verified at all three gates.

## Day 3 — Cutover playbook + finish (Nov 18, 2026)

- Built `playbook/` with five files: `README.md` (Day 3 overview), `phased-cutover-plan.md`, `parallel-run-validation.md`, `rollback-criteria.md`, and `reporting-continuity-mci.md`.
- Phased cutover: Wave 0 foundation only — SEG-00 reconciled with DE-05, consent sync proven at all three gates, shared domains confirmed, MCI baseline, and Retires J-06 / A-04 switched off. Then one Moves journey per wave: Wave 1 J-05 dormant re-engagement (SEG-04, the parallel-run proof), Wave 2 J-02 card activation (DA-01 event path), Wave 3 J-01 onboarding (by join-date cohort, after A-04 retirement removes duplicate entry), Wave 4 J-04 savings / CD maturity as two sub-waves (SEG-03a then SEG-03b, gated on real date fields). Each wave names entry and exit criteria; Stays assets (J-03, J-07, CP-01) keep running and are the rollback safety net.
- Parallel-run validation: shadow stage (audience only, nothing sends from Next), then split-live stage (distinct cohorts, zero overlap). Audience-count comparison table (gross / suppressed by reason / consent-excluded / net sendable / entered / exited), investigated only in Day 2's parity order — definition, data completeness, identity, consent. Suppression parity by member and by reason, with Automation Studio SQL Q-P1 (counts by reason, DE-05 vs Data 360 feed), Q-P2 (suppressed-in-Engagement-but-missing-in-feed — the zero-row stop condition), Q-P3 (net sendable for J-05), and Q-P4 (duplicate-entry guard). Plus consent-sync spot checks on invented test members and Stage B send-behaviour checks (no duplicates, exit behaviour, personalisation spot check, bounce/complaint feeding suppression).
- Rollback criteria: five immediate rollback triggers (suppressed member sent to, opt-out not honoured, duplicate sends, sends continuing on degraded consent sync, a trigger firing for a Stays/Retires asset), five pause triggers (unexplained count difference, by-member suppression mismatch, exit divergence, deliverability divergence, unreconcilable reporting), who decides (anyone can pause on a suppression breach; wave owner decides rollback), and a six-step rollback execution that re-points entry to the intact paused Engagement journey without weakening suppression.
- MCI reporting continuity: one programme view per journey with platform as a dimension, harmonised dimensions (journey ID, stable message names, channel, cohort, one date convention) frozen during waves, Engagement source unchanged plus Next source mapped to the same dimensions, Wave 0 baseline, per-wave comparison windows, and continuity that survives rollback, retirement, and the end of the playbook. No performance targets or metrics are set — Northstar is fictional and none exist.
